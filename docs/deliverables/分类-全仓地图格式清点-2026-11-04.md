### 1.5 ★ 三个必须知道的硬事实（会改变"全量支持"的口径）

**① C# 的 `Type3` 分支对这 195 张真实 36B 图 100% 打不开。**
195 张全部满足 `len == 52+36·w·h`，而 C# `:286-304` 每格推进 **40** 字节 ⇒ 需要 `52+40·w·h`，对任意 `w·h≥1` 恒 `> len` ⇒ 循环末尾越界 ⇒ `:322` 统一包成 `InvalidDataException("Invalid or truncated map file.")`。
这与规格书 §四「能识别、必然读失败」完全一致，本轮**在真实数据上得到 195/195 的实证**。
**全仓 Type3-40B（`len==52+40·w·h`）为 0 张** ⇒ C# 这条分支在本仓**没有任何一张能读成功的文件**。

**② C# 的 Type2 签名 `B[4]==0x0F` 与「14 字节/格」不相关。**
- 12B/格 文件的 `B[4]`：`0x0D`（787 张）、`0x2E`（4 张）、**`0x0F`（4 张，即 §5.3 那 4 张被误判成 Type2 的）**
- 14B/格 文件的 `B[4]`：`0x0F`（122 张）、`0x03`(4)、`0x07`(16)、`0x0B`(6)、`0x0D`(2)、`0xFF`(2)、`0x00`(2)
⇒ `0x0F` 既出现在 12B 里，也缺失于 14B 里。**真正的判别量是文件长度**（`B[18..19]==0x0D 0x0A` 亦非必要：14.map 的 `B[18..19]=0x00 0x00` 仍是 14B/格）。

**③ 36B/格 = 14B 结构 + 22 字节全零填充（本轮独立佐证了 `AGENTS.md` §二·五）。**
零字节残差谱（§六 6.2）显示：`FIGHTING.map` 在 stride=36 下，前 14 个残差位有结构（`0.75 0.88 0.93 0.94 0.86 0.41 1.00 1.00 1.00 1.00 0.86 1.00 0.75 0.93`），**后 22 个残差位全为 `1.00`（100% 零）** ⇒ 36 = 14 + 22 零填充，与记忆一致。

**★ 卡点（这就是"无法归类"的准确表述）**

1. **12 字节周期是真的**，不是噪声。用「零字节残差谱」与真 Type0 对照：

| 文件 | stride=12 各残差位零字节占比 |
|---|---|
| 真 Type0 `0.map`（700×700） | `0.46 0.31 0.98 1.00 0.94 0.94 1.00 1.00 1.00 1.00 1.00 1.00` |
| **EM001.map** | `0.75 0.37 1.00 1.00 0.94 0.49 1.00 1.00 1.00 1.00 0.94 1.00` |
| **T218.map** | `0.75 0.41 1.00 1.00 0.93 0.55 1.00 1.00 1.00 1.00 0.93 1.00` |
| 真 Type2 `11.map`（14B） | `0.77 0.80 0.81 0.80 0.77 0.80 0.81 0.80 0.77 0.80 0.81 0.80`（**平坦，无 12B 结构**） |

   三者的"残差位 2/3/6/7/8/9/10/11 全零"特征**同型** ⇒ EM/T 组与 Type0 是**同一类 12B 格布局**；而 stride=14 的残差谱对 EM001 是 `0.93 0.81 0.93 0.81 ...`（平坦）⇒ **14B 被排除**。
   自相关也一致：`s=12 → 0.900`、`s=24 → 0.949`、`s=36 → 0.884`（基线 `0.741`）。

2. **但格数对不上头部**：`(20692−52)/12 = 1720` 格，而 `w·h = 1050`（EM 组）或 `900`（T 组）。
3. **长度与 `w·h` 完全无关**：`EM001`(30×35) 与 `T218`(30×30) **同为 20,692 B 但内容不同**（SHA256 不同）⇒ 文件大小**不由 `w·h` 决定**，这排除了"任何 `w·h` × 整数格长"的可能。
4. 数据实际延伸到偏移 **20,165**（最后一个非零字节），即约 **1,677 格**；尾部 527 B 为全零。
5. **不排除**是「固定 20,692 B 的占位/预分配文件」或「头部 `w·h` 与格数组描述的不是同一张图」，但**没有证据支持任何具体解释** ⇒ 按「禁编数据」纪律，**标为无法归类，不硬塞进任何格式**。

## 六、口径与局限

### 6.1 口径

1. **判别口径 = C# `LegacyMapReader.initiate()` `:55-117` 的 if-else 短路顺序**（先命中先返回，兜底 Type0），与规格书 §〇 0.2 表逐条对应。

## 附：一条结论作废（2026-11-05 00:xx 订正）

本报告「三个会改口径的硬事实」第 1 条原文：

> **C# 的 Type3 分支对全部 195 张真实 36B 图必抛 `Invalid or truncated map file.`**（每格实读 40B，`52+40wh > len` 恒成立）

**该结论作废。** C# 的 `LoadMapType3` 每格实际推进 **36 字节**（不是 40），**能正确读全部真实 36B 文件**。

- **根因**：`LegacyMapReader.cs:300` 与 `:303` 的 `ToInt16(Bytes, offset)` **不推进 offset**，其 2 字节落在 `:301` 的 `+= 7` 与 `:304` 的 `+= 14` 跳过区**内部**；本报告沿用了规格书 §四 的错误推导（把两次"只读不推进"当成额外推进，多算 4 字节），**未独立复算 offset**。
- **实证**：194 个真实 36B 文件，按 36B/格 逐句复算，**末 offset 全部恰好等于文件长度**（194/194）；`len == 52+40·w·h` 的文件 **0 个**。
- **不受影响**：本报告的**张数统计**（Type0 890 / Type3-36B 195 / Type2 122 / 无法归类 67）与**分类结果**全部有效 —— 错的只是"读取实现"那一句评价。
- 详见 `规格-地图格式全量9种-2026-11-04.md` **§十三**（逐句表 + 实证）。
