# 审查：六种零真实样本地图格式 —— Rust ↔ C# 逐行对照

- **日期**：2026-11-05
- **性质**：**只读审查**（本轮只新建本文件，未改任何已存在文件）
- **对照源**：
  - C#：`E:\GodM2\CrystalStudio\CrystalStudio\LegacyMapReader.cs`（667 行）
  - Rust：`E:\GodM2\tools\miredit\crates\mir2-format\src\formats\*.rs` + 公共模型 `..\src\model.rs`
- **风险前提**：9 种格式里只有 Old12（856 张）/ Shanda14（107 张）/ Shanda2012（195 张）有真实样本。
  本文件审的 6 种**零真实样本**，其实现只由「按我们对 C# 的理解手写的合成样本」支撑
  ⇒ **理解错 ⇒ 样本也错 ⇒ 往返照样绿**。所以本审查**不看测试是否绿**，只看两边的字节流水账。

## 方法

1. 把 C# 每个 `Bytes[offSet += N]` / `ToInt16(Bytes, offset)` / `Skip(N)` 抄成「字节流水账」（偏移 → 宽度 → 字段）。
2. 把 Rust `read` 抄成同样的流水账。
3. 两账逐行比：偏移 / 宽度 / 字段顺序 / 多读少读。
4. 专门盯「读不推进 offset」的陷阱：`BitConverter.ToXxx(Bytes, offset)` **不推进** `offset`，
   只有显式的 `offset += N` 或 `++offset` 才推进。C# 里两种写法混用，是历史上两次误算的根因
   （Type1 曾误记 17 B/格、Type3 曾误记 40 B/格）。
5. 再比 `write` 是否与 `read` 严格镜像。

### 1.3 差异清单（4 条）

**D1.1 🔴 `csharp_has_front` 语义错：C# 在本支是「无条件有前景」**

- Rust：`wemade2010.rs:414-417` `csharp_has_front(fr_img) = (fr_img & 0x7FFF) > 0`；模块文档 `:91` 也把它写成「有前景 ⇔ `(wFrImg & 0x7FFF) > 0 && (btArea+2) > 0`」。
- C#：`LegacyMapReader.cs:202` —— **`HasFront = true,`**（对象初始化器里的**常量赋值**，本支根本没有 `if`）。
  与之对照：`Type0 :151` / `Type2 :253` / `Type3 :309` / `Type4 :364` 才是「`(frimage & 0x7FFF) > 0 && frindex > 0`」。
- **正确值**：Type1 的 `HasFront` 恒 `true`（`heroes34.rs:215-217` 对结构完全同形的 Type7 就是这么写的：`csharp_has_front() -> true`）。
- **影响面**：`HasFront` 是渲染层「画不画前景」的开关。C# 认为**每一格**都有前景；Rust 的 helper 认为 `fr_img` 低 15 位为 0 的格**没有**前景 ⇒ 这类格（空前景格，占多数）的前景层不会画。
  另外 `:207` 的 `if (HasFront)` 因恒真而等价于无条件执行 —— Rust 的 `csharp_back_mark`（`:420-426`）**恰好是对的**（没有把 `has_front` 当条件），所以这一处只有 helper 语义错，字节层无影响。
  当前全仓 **无生产调用点**（`csharp_*` 只在各模块 `#[cfg(test)]` 里被调用，`grep` 110 处命中全部在 `mir2-format` 内）⇒ 属「API 语义错，接线后才发病」。

**D1.2 🔴 自造「17 B/格」备档：C# 里不存在，且会静默读错**

- Rust：`wemade2010.rs:126` `CELL_LEN_ALT = 17`、`:132` `TAIL_LEN_ALT = 3`、`:160-171` `cell_len_of`、`:244-267` 17 B 读分支、`:298-320` 17 B 写分支。
- C#：**没有第二档**。`:183` 的 `ValidateDimensions(54, 15)` 与 `:174-205` 的逐句推进共同钉死 15 B/格（本文件 §1.1 已逐句复算）。
- **正确值**：只有 15 B/格一档。
- **影响面（这是本格式最危险的一条）**：
  1. 若真文件是 **15 B/格 + 恰好 `2·w·h` 字节尾随**，长度就等于 `54 + 17·w·h` ⇒ 被判成 17 B 档，**每格起点漂移 2 字节**，全图除前 3 个字段外**全部字段错位**；而 `write` 严格镜像 `read` ⇒ **往返仍然逐字节相等，测试照样绿**。这正是「理解错 ⇒ 样本也错 ⇒ 往返照样绿」的教科书形态。
  2. `detect`（`:183-189`）也接受 17 B 档 ⇒ 该错读不会被判别层拦住。
- ⚠ 模块文档 `:73-75` 自己已写明「两档都未经真实样本验证」，但代码仍把 17 B 当合法档**读进来**，而不是「报 `UnsupportedVariant` 等人判」。

**D1.3 🟠 `read` 比 C# 严格：带尾随字节的真文件「连宽松入口都读不了」**

- Rust：`wemade2010.rs:229-243` —— 长度既不等于 `54+15n` 也不等于 `54+17n` ⇒ 直接 `Err(UnsupportedVariant)`。
- C#：`ValidateDimensions`（`:47-54`）只查「够不够」，**不查「是否恰好」** ⇒ 多出的字节被静默丢弃，文件照读。
- **影响面**：`read_any` 会报 `LengthMismatch`；`read_any_tolerant` 也会失败 —— 因为 `registry.rs:200-204` 只用 `expected_len` 判「够长」，随后仍调 `Wemade2010::read`，而它**自己又判一次精确长度**。
  ⇒ **本格式是九种里唯一「尾随字节 ⇒ 完全读不了」的**（其余 5 种本文件审的格式 + Old12/Shanda14/Shanda2012 的 `read` 都容忍尾随并把它放进 `trailer`，见 `model.rs:638` / `mir3_wemade.rs:225`）。
  而本仓已实测**真实地图确实存在尾随字节**（`model.rs:67-70`：67 个文件、每张多 8,040 字节）⇒ 这个严格度不是理论风险。

**D1.4 🟡 `csharp_back_mark` 的参数没说明「要传 XOR 还原后的值」**

- Rust：`wemade2010.rs:420-426` `csharp_back_mark(back, fr_img)`；`fr_img` 参数名与 `Cell::fr_img`（磁盘原值）同名。
- C#：`:209` 判的是 `MapCells[x, y].FrontImage & 0x8000`，而 `FrontImage` 在 `:196` 已经 `^ xor` 过。
- **影响面**：若上层直接把 `cell.fr_img`（磁盘值）传进去，`xor` 的 bit15 为 1 时阻挡标记会判反。同理 `csharp_back_image(raw)`（`:379-381`）**内部会** XOR（正确），两个函数一个 XOR 一个不 XOR、参数名却都叫 `raw`/同名 —— 契约不一致。当前无调用点。

### 1.4 小结

- **字节流水账：逐行一致**（15 B 档，字段偏移/宽度/顺序/跳过区全对，`write` 严格镜像）。
- **语义层有 1 条真错**（D1.1，C# `HasFront = true` 被写成条件式），**1 条自造档位**（D1.2，风险最高），**1 条过严**（D1.3，会让真文件读不了）。

**D4.1 🟠 漏掉 Type5 里**活着**的那条前景哨兵规则 `frimage==1 && frindex==200 ⇒ frindex=-1`（C# `:429-430`）**
