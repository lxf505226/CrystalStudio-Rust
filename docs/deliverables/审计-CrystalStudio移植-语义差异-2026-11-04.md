## 三、真错误清单（必须修）

### E1 🔴 高 · 素材面板「图号」是 0 基，写进 `bk_img`（1 基）⇒ 落格整体差 1

**现象**
从素材面板点选一帧（或 `--palette-pick N`）当笔刷，画到地图上，**画出来的永远是库里的上一张图**；选「0 号帧」时格子变成**没有地表**（且不报错、不提示）。

**证据链（五段闭合）**
1. 面板的 `index` 是 **0 基帧索引**：`palette.rs:823`（`idx = row*8+col`）→ `palette.rs:908`（`src.frame_of(key.lib, key.index)` 直接按该索引解码并显示）→ 实测截图 `layout/refs/ours-palette.png`：分页「896-943 / 共 31775 帧」、当前素材「地表层 · Tiles · **图号 904**」。
2. 该索引被**原样**写进笔刷：`dock_right.rs:713-716`（AA 行 `("img", &key.index.to_string())`）→ `app.rs:900` / `app.rs:1063`（`set_brush_from_palette(key.lib, key.index)`）→ `edit.rs:401-406`（`Brush { bk_img: img as u16 }`）。
3. 笔刷被**原样**写进地图格：`edit.rs:479-482`（`out.bk_img = b.bk_img`）。
4. 渲染侧按 **1 基**解释：`compose.rs:98-103`（`let bk = cell.bk_img & 0x7FFF; … cache.get(lib, bk-1)`），且 `bk==0` 直接跳过（`compose.rs:99-101`）。
5. 客户端真值也是 1 基：`map_loader.gd:51-52`（「帧号是 **1-based**，取图前先 `-1`」）、`map_loader.gd:167-168`、`GameScene.cpp:3567-3577`（`nImgNumber = wBkImg & 0x7FFF; if (>0) nImgNumber -= 1`）。

**影响**
- 编辑器的核心动作（选帧 → 落格）**每一次都错一格**，且错得很安静（画面上就是"贴了块地"，看不出差一帧）。
- 选 0 号帧 ⇒ `bk_img = 0` ⇒ 客户端/渲染器都判为「该格没有地表」，等于**把一个有地表的格子改成了空格**，`dirty` 却是真的。
- 同一面板内还有第二处口径冲突：素材面板/状态栏的「图号」= 0 基帧索引，而单元格信息面板的「图号」（`cellinfo.rs:94-97`，`bk_img & 0x7FFF`）= 1 基图号。**同一个词、同一个数字，指两帧**（截图里 状态栏「笔刷：地表 图号 904」而画布上实际是帧 903）。
- 闸门也按 0 基判：`palette.rs:784`（`key.index > SPRITE_MAX`），应为 `index + 1 > 0x7FFF`。

**建议改法（不要求我改）**
1. `edit.rs::set_brush_from_palette`：`let img1 = img + 1; if img1 > SPRITE_MAX as u32 { return None }`，`bk_img = img1 as u16`；函数文档明确「`img` 是 0 基帧索引，落格写 `img+1`」。
2. 显示口径二选一并全仓统一：要么面板显示 `index+1`（推荐，与地图格/客户端一致），要么把标签改成「帧索引（0 起）」并在同处显示对应 `图号 = index+1`。
3. `palette.rs:784` 的闸门改 `index + 1`；`PALETTE_SEARCH_OUT_OF_RANGE_TMPL`（`ui_text.rs:226`）的「0-{max}」同步。
4. 补一条必定能红的往返测试：`set_brush_from_palette(ground, N)` → `paint` → `map.cell(...).bk_img == N+1` → `compose` 解码的帧号 `== N`；再补 `N=0 ⇒ bk_img==1`（当前实现会写成 0，测试必红）。

### E3 🟠 中 · 缩放档变化不触发重渲，纹理过滤永久停在装载时那一档

**现象**
`CanvasView::ensure` 的缓存命中判定只看 `map_gen / mask / 覆盖范围`，**不含 `scale`**；而 `texture_options()`（整数倍 NEAREST、非整数倍 LINEAR）只在 `load_texture` 那一刻生效。于是在同一张缓存纹理存活期间改缩放，过滤方式不会跟着变。

**证据**
- `canvas_view.rs:229-239`：`up_to_date = c.map_gen==map_gen && c.mask==mask && 覆盖…`（无 `scale`）。
- `canvas_view.rs:200-207` + `:288-292`：`texture_options()` 仅作为 `ctx.load_texture(...)` 的入参。
- `canvas_view.rs:41-44` 与 `:424-438` 的文档/测试都写「整数倍 NEAREST / 非整数倍 LINEAR」。

**影响**
- 以 1× 起步：放大到 1.5× / 2× / 3× 全程 NEAREST ⇒ 非整数倍下出现马赛克抖动（正是文档说要避免的）。
- 以 0.25× 起步（`--fit` / `Fit Map`）：放大到 1× / 2× 全程 LINEAR ⇒ 像素级 1:1 时发糊，截图逐点比对失真。
- `整数倍用最近邻` 这条单测**测不到**它（只测纯函数），所以这个错一直绿着（见下「测试空转」）。

**建议改法**
- 命中判定加一档「过滤档变了也重渲」：`c.filter_class == self.filter_class()`（`NEAREST|LINEAR` 二值，不必按 scale 精确比）。
- 或改在绘制时用 `TextureHandle::set(..., options)` 重设（若所用 egui 版本支持）——需实测。
- 加断言：`scale 1.0 → 1.5` 后 `render_calls` 至少 +1，且新纹理的过滤方式是 LINEAR。

**附注（余量 10 格的临界）**
`metrics.rs:303-318` 自己写「实测最大帧体 300~500 px」又写「10 格 = 480 px 已覆盖实测最大帧体」——**480 < 500**，算术上不成立（500 px 需 11 格）。实测命中率在 10/14/20 格都饱和到 99.96%，所以实践上够用；但那句话应改为「实测出现的最大帧体 ≤ 480 px」或把余量提到 11 格，否则是"数字与自己的依据不符"。

### E5 🟡 低 · 缺 16M 格上限护栏

### E7 🟡 低 · 保存无 `fsync`，「读回核对」证明不了落盘

**证据**：`save.rs:18-21` 声称读回核对能防「缓写、磁盘满时的短写」；实现 `save.rs:51`（`std::fs::write`）与 `:63`（`std::fs::read`）都走 OS 页缓存，全程无 `File::sync_all()`；rename 后也没有目录 fsync（Windows 上后者可省略，前者不可）。

**影响**：断电/蓝屏后仍可能丢失或得到半截文件——**「读回核对」并不构成抗断电证据**。同时注意：`save.rs` 的**主干保证（不截断原文件）是成立的**（临时文件 + rename），失败路径也确实清临时文件。

**建议改法**：写临时文件后用 `File::sync_all()`（或 `sync_data`），再核对、再 rename；把 `:18-21` 的说法改成「防短写与并发覆盖，抗断电需 fsync」。
