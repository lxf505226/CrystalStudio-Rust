- **后果 A（文案）**：删除选区/贴印章时，`selection.rs:398-404` 会输出
  「`Old12` 里 `物体图层` 的库号字节没有对应字节（writer 不写它）—— 该字节未清零，只清图号」
  —— **这句话是错的**：字节存在、writer 也写。

  ```csharp

  w.Write(f?.Library ?? (short)0); w.Write(f?.Image ?? (short)0); …
  ```

- **Rust**：`selection.rs:166-171`
  ```rust

  (b as u32 - a as u32 + 1) as u16
  ```
  65536 `as u16` = **0**。注释声称避免溢出，实际只是把溢出推迟到最后一次窄化。

### 6.2 缺陷

#### 【P1-9】`editable=false` 覆盖 8/9 格式 ⇒ **1,051 张真实图被常驻假告警**（实测日志）

- **Rust**：`mir2-format/src/formats/*.rs` 的 `caps().editable` —— 只有 `shanda14.rs:202` 是 `true`，
  其余 8 种（含 **`old12.rs:167`** 与 **`shanda2012.rs:364`**）都是 `false`。
- **消费方**：`miredit-core/src/document.rs:240-245`
  ```rust
  if !self.caps().editable {
      parts.push(format!("本格式（{}）未解区语义未知，编辑仅保证字节保真，不保证动画/联动正确", …));
  }
  ```
  GUI 按**常驻黄条**显示（`banner.rs:9`），不是 toast、不自动消失。
- **实测证据**（我跑 门2门3 的 stderr 原文，摘 3 行）：
  ```
  [地图] 告警：本格式（Old12（12B/格，TMapInfo 旧版））未解区语义未知，编辑仅保证字节保真…
  [地图] 告警：本格式（Shanda2012（36B/格，14B 字段 + 22B 未建模尾区））未解区语义未知…
  [地图] 告警：本格式（Shanda2012…）未解区语义未知…
  ```
  ⇒ 856 张 Old12 + 195 张 Shanda2012 = **1,051 / 1,158 张（90.8%）真实图**都会挂这条黄条，
  包括缺省打开的 `0.map`（Old12）。
- **为什么这是"假告警"**：
  1. `Old12` 的 12 字节**全部有名字**（`old12.rs:129-140` 读 bk/mid/fr/door/door_offset/ani_frame/ani_tick/area/light），
     `lost_fields(Old12)` 是**空**（`convert.rs:258`）⇒ **它没有"未解区"**；
  2. 它有 **856 张真实样本**、逐字节往返 0 差异（§6.1），`caps().has_real_samples = true`（`old12.rs:172`）。
  3. 于是文案里的"未解区语义未知"对 Old12 是**事实错误**。
- **影响面**：**告警疲劳** —— 90% 的图一打开就有一条黄条，用户很快学会无视它；
  而真正需要看见的那条（67 张 `trailer=8040` 的"整图可能错位"）**就排在同一条黄条里**（`document.rs:233-239` 拼在同一个 `parts`）。
  这是"真告警被假告警淹没"的典型。
- **正确值**：`editable` 应按"**该格式有没有未建模字节**"判，而不是按"我敢不敢承诺"判：
  `Old12`（零未建模）/ `Shanda14`（零未建模）应为 `true`；`Shanda2012`（22 B 未建模）保留 `false` 是对的。

#### 【P2-20】`sync_document_format` 的早退判据**不是单射**（9 格式 → 3 档投影）

- **Rust**：`edit.rs:365-378`
  ```rust
  if view_cell_format(self.core.document().format_id()) == map.format && (rw, rh) == (map.width, map.height) { return; }
  ```
- **判据的像只有 3 个值**（`convert.rs:296-309`）：`Old12` / `New14` / `Ext36`。
  而 `Old12|AntiHack|Wemade2010|Heroes34 → Old12`、`Shanda14|Mir3Wemade|Mir3Shanda|CrystalCs → New14`。
- ⇒ 若把一张 **`CrystalCs`** 图塞进一个已绑定 **`Mir3Wemade`** 的会话（同尺寸、同投影 `New14`），
  判据**早退**，`raw.format` 仍是 `Mir3Wemade` ⇒ `ground_paint_supported` 返回 `false`
  （`convert.rs:543-545`），**地表笔刷在 CrystalCs 图上被错误拒绝**。
- **可达性**：生产路径 `app.rs:262-272` 只在启动时 `bind_document` 一次，GUI 只支持单图
  （`mapdoc.rs:214` "本单只支持一张图"）⇒ **当前不可达**。属**潜伏缺陷**。
- **正确值**：判据应比较 `format_id()` 的**全等**（而非三档投影），或干脆比 `orig_bytes` 指针/哈希。
- 注：`edit.rs:363-364` 自己写了"这条重建路径**只对 12/14/36 三档保真**"——
  说明作者知道有边界，但没意识到**早退判据**本身也是三档。

#### 【P2-21】`bind_document` 造出**第二份** `Document`（整份字节 + 整份 raw 再解析一遍）

- **Rust**：`edit.rs:294-302` —— `Document::from_bytes(path, bytes.to_vec())`：
  `bytes.to_vec()` 复制整份文件，再走一次 `read_any_tolerant` 解析出**第二份 `raw.cells`**。
- 与此同时 `MapDoc.document`（`mapdoc.rs:60`）**也**持有一份 `Document`，`MapDoc.map` 还持有一份 `view` 克隆（`:82`）。
- **算一下 `0.map`（700×700 = 490,000 格）的量级**：
  | 对象 | 数量 | 单件 | 小计 |
  |---|---|---|---|
  | `orig_bytes` | 2 份 | 5.88 MB | ≈ 11.8 MB |
  | `raw.cells`（`Cell` 含 `Vec<u8> tail`，≈ 40 B 结构 + 24 B Vec 头 + 22 B 堆 ≈ 86 B/格） | 2 份 | 490,000 × 86 B | ≈ 84 MB |
  | `view.cells`（`mir2_map::Cell` 定长 ≈ 37 B） | 2 份（`MapDoc.map` + 各 `view`） | 490,000 × 37 B | ≈ 36 MB |
  | **合计** | | | **≈ 130 MB** |
- **影响面**：一张 700×700 图 ≈ 130 MB 常驻；`ygfx1.map`（800×800，实测 23 MB 文件）会更高。
  对一个"打开就常驻"的桌面编辑器来说，这是**可优化**而非"错"，但在 4 GB 机器上会明显。
- **正确值**：`EditSession` 只需 `format_id + width + height`（三处闸门只读这三个值，
  见 `edit.rs:278-285` 的表），不必持有整份 `Document`。

#### 【P2-22】`touched_cell()` 对"改多格"的命令只给**锚点**或 `None`

- **Rust**：`miredit-web/src/json.rs:173-198`：`Fill`/`PlaceStamp`/`PasteSelection` 只返回**一格**坐标；
  `DeleteSelection`/`FillSelection` 返回 `None`。
- **实际语义**：这些命令分别会改**整片连通块 / 整枚印章 / 整个矩形选区**。
- **影响面**：`json.rs:169` 自己写"只用于 `/api/events` 的 `rerender` 区域提示（前端目前整屏重取）"⇒ 当前无害。
  但函数名叫 `touched_cell`、注释说"这条命令影响的格坐标"，**名字与语义不符**；
  一旦前端改成按区域重绘，就会漏刷。
- **建议**：改名 `anchor_cell()`，或返回 `Option<Rect>`。

### 6.3 做对的地方

- `Document::try_to_bytes(&self)` **克隆 raw 再同步**（`document.rs:289-295`）⇒ 保存失败**不会**污染内存里的 `raw`，
  也不会出现"存失败了但内存以为存上了"。这是"先算后写"在字节层的正确落地。
- `MapDoc::to_bytes` 的 `swap` 顺序正确（`mapdoc.rs:167-172`：`swap → try → swap → 返回`），
  失败时**不回退**到 `map.to_bytes()`（`:165-166` 明写理由）。
- `core_err_text`（`mapdoc.rs:344-351`）把 `CoreError` 包装层剥掉、**不加工文案** ⇒ 迁移前后状态栏文案逐字一致。

  `mapdoc.rs:272-274` 同时打 stderr。**三层都接上了**，不是只在注释里说。
- 门 4 从"注入档位"改成"**真写一个 Type5 文件到磁盘再打开**"（`acceptance_tests/formats.rs:29-35`）——
  这是把假验证换成真验证，方向正确。

## 8. 契约漂移（`Command` 19 变体 / `Outcome`）

### 8.1 `Command`：三端**没有**漂移

| 端 | 位置 | 做法 | 结论 |
|---|---|---|---|
| core 定义 | `cmd.rs:71-206` | 19 个变体：`SetLayer`/`SetBrushSize`/`SetTool`/`PlaceStamp`/`Paint`/`Stroke`/`Erase`/`Fill`/`Pick`/`SetSelection`/`ClearSelection`/`CopySelection`/`CutSelection`/`PasteSelection`/`DeleteSelection`/`FillSelection`/`Undo`/`Redo`/`Save` | — |
| web 直译 | `miredit-web/src/json.rs:142-165`（`name`）、`:209-341`（`parse`） | 两处都是**穷举 match、无 `_` 臂**（`:139-141` 明写"内核一加变体这里就编译红"） | ✅ 19/19 覆盖 |
| gui 转发 | `miredit-gui/src/edit.rs:383-392` | `miredit_core::apply(core, cmd)` **不 match 变体** | ✅ 无需跟随 |

**核实过的点**：
- `name()` 的 19 个字符串与 `parse()` 接受的 19 个字符串**一一对应**（我逐条比对过：`SetLayer`…`Save`）。
- `json.rs:106-107` 记着一条历史事故：「早先是 `_ => None` 兜底，`Erase` 就这么漏过」⇒ 现在是编译器强制，**这条修得对**。
- `cmd.rs:55-56` 记着另一条：「`miredit-web/src/error.rs:117-128` 对 `CoreError` 做穷尽 match，新变体会让那个 crate 编译不过」
  ⇒ **`CoreError` 与 `Command` 两个契约都被编译器钉住了**。

### 8.2 `Outcome`：三端语义一致，但"`changed==0` 必有 `note`"只靠约定

- **定义**：`cmd.rs:209-221`（`changed` / `note` / `dirty` / `can_undo` / `can_redo`），**三端共用同一个结构体**（web/gui 都直接用 `miredit_core::Outcome`）⇒ 无漂移。
- **不变量**：`cmd.rs:34-39` 声明「每条命令在 `changed == 0` 时都**一定**带一句原因」。
  我核了 `cmd.rs` 里全部 7 处 `outcome(0, …)`：**7/7 都传 `Some(note)`**（`:243`/`:247`/`:369`/`:379`/`:393`/`:487`/`:512`）⇒ **当前成立**。
- **但**：`session.outcome(changed, note)`（`session.rs`）的签名允许 `(0, None)`，
  **没有任何类型或断言拦住**。一旦新加一条命令忘了写 note，就是静默失败。
- **建议**：把 `outcome()` 拆成 `outcome_ok(changed, note)` 与 `outcome_noop(note: String)`（`note` 非 `Option`），
  让"改了 0 格却没说原因"**编译不过**。这一条与 `json.rs` 的"无 `_` 臂"是同一个思路，值得统一。

### 8.3 一处**同名不同物**的坑（已记档，但值得单独点名）

- `miredit-gui/src/app.rs` 里的 `Command::` 是 **egui 的 `ViewportCommand`**，不是内核的 `miredit_core::Command`
  （`json.rs:112-113` 明写"同名不同物"）。
- 同一个 workspace 里还有**两个 `scale`**：`Viewport.scale`（`f32`，**必须 1.0**，否则 `UnsupportedScale`）
  与 `CanvasView.scale`（`f32` 画布缩放，可 0.25~4.0）。`cli.rs:176` 的 `--scale` 设的是后者。
- **风险**：新人把 `RenderScale::Half` 传给 `Viewport.scale` 会直接报错（好），
  但把 `CanvasView.scale = 0.5` 当成"半倍渲染"就会以为多倍率已生效（实际只是 egui 纹理缩放）。
  ⇒ 这是 **P1-25（多倍率零调用点）** 会被误判成"已接线"的直接原因。
